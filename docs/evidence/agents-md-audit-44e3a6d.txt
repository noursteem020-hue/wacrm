## 2. Rule 10's stated mechanism is false. The pipe does not convert CR

Rule 10 and the ledger both say `git show <commit>:<path> | md5sum` differs from
the committed bytes because the pipe converts CRLF. Measured at HEAD, on four
files including the two the ledger names: the pipe is byte-identical to the blob.

```
for f in docs/evidence/b2/executor.jsonl docs/evidence/b2r2/executor.jsonl docs/evidence/suite/npm-test-tip.txt docs/evidence/suite/tsc-tip.txt; do blob=$(git cat-file blob HEAD:$f | md5sum | cut -d' ' -f1); show=$(git show HEAD:$f | md5sum | cut -d' ' -f1); wtree=$(md5sum "$f" | cut -d' ' -f1); blobcr=$(git cat-file blob HEAD:$f | tr -dc '\r' | wc -c); wcr=$(tr -dc '\r' < "$f" | wc -c); printf '%-46s blobCR=%-3s wtCR=%-3s pipe==blob:%s  wtree==blob:%s\n' "$f" "$blobcr" "$wcr" "$([ "$blob" = "$show" ] && echo YES || echo NO)" "$([ "$blob" = "$wtree" ] && echo YES || echo NO)"; done
```

```
docs/evidence/b2/executor.jsonl                blobCR=0   wtCR=14  pipe==blob:YES  wtree==blob:NO
docs/evidence/b2r2/executor.jsonl              blobCR=0   wtCR=14  pipe==blob:YES  wtree==blob:NO
docs/evidence/suite/npm-test-tip.txt           blobCR=0   wtCR=0   pipe==blob:YES  wtree==blob:YES
docs/evidence/suite/tsc-tip.txt                blobCR=0   wtCR=0   pipe==blob:YES  wtree==blob:YES
```

The conversion is real and it happens on **checkout**, not in a pipe:
`core.autocrlf=true`, so the blob holds 0 CR and the working tree holds 14. A
`git hash-object` of the working file returns the blob oid anyway, because
autocrlf normalises on the way in. So the rule's advice is right and its reason
is wrong:

```
git config --get core.autocrlf
md5sum docs/evidence/b2/executor.jsonl
git hash-object docs/evidence/b2/executor.jsonl
git rev-parse HEAD:docs/evidence/b2/executor.jsonl
```

```
true
bb3bf3764ad63284e5d3a2ec0cee53ee   (working bytes)
21e4a7383feb002d7859ba3c35bd93dcd7b9f666   (git hash-object, working bytes)
21e4a7383feb002d7859ba3c35bd93dcd7b9f666   (git rev-parse, committed bytes)
```

### 2b. A measurement trap that produced a false 14 in this very session

`grep -c $'\r'` was reported as "14 CR in the blob" in an earlier run of this
audit. The pattern is unreliable: when it collapses to empty, `grep -c ''`
returns the LINE COUNT. Proven with a 4-line control file:

```
printf 'a\nb\nc\nd\n' > control.txt; grep -c '' control.txt; grep -c $'\r' control.txt
```

```
4
0
```

The reliable spelling is `tr -dc '\r' | wc -c`, used above.
